# MatFlow 前端开发计划：实用型流式工作流 WebUI

**状态：仅规划，暂不执行**  
**适用阶段：MatFlow WebUI v0.2 及后续迭代**  
**关联文档：** `ARCHITECTURE_AND_DEVELOPER_RULES.md`、`BACKEND_API_CONTRACT.md`

## 1. 目标与设计判断

MatFlow 前端不以复刻 ComfyUI 的外观为目标，而是建设一个面向材料学研究工作流的**可操作、可观察、可调试**的 WebUI。

核心问题不是“画布是否像节点编辑器”，而是用户能否清楚回答：

- 当前工作流有哪些节点，节点之间传递什么类型的数据？
- 哪些节点已经完成，哪些正在等待，哪些被错误阻塞？
- 当前节点实际收到了什么输入，产生了什么输出？
- 后端为什么选择这个工具？参数和端口是否通过验证？
- 流式执行过程中发生了什么，失败后能否定位并重试？
- 前端显示的状态是否来自后端真实状态，而不是浏览器自行推断？

### 1.1 设计原则

1. **状态优先**：画布是 GraphState 的可视化，不是独立的本地真相。
2. **操作就近**：节点操作放在节点或其 Inspector 附近；影响整个工作流的操作放在顶部。
3. **执行可见**：排队、运行、流式输出、等待人工确认、成功、失败和取消都必须可区分。
4. **证据可追溯**：路由理由、校验结果、执行结果和 trace ID 都能从界面中查到。
5. **前后端职责分离**：前端负责展示和收集意图，后端负责类型兼容、校验、图变更和执行决策。
6. **不要复制 ComfyUI 的信息密度**：节点内部只展示操作所需的摘要，详细参数、日志和结果进入 Inspector/Console。
7. **先建立领域模型，再做视觉细节**：节点、端口、边、执行、事件和产物必须有稳定含义。

## 2. 目标信息架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 工作流名称  保存状态  运行全部  停止  当前 Graph version     │
├────────────┬───────────────────────────────┬────────────────┤
│ 节点库      │                               │ Inspector      │
│ 搜索/分类   │          Workflow Canvas      │ 当前节点       │
│ 节点说明    │                               │ 参数/端口       │
│             │                               │ 输入/输出/日志  │
├────────────┴───────────────────────────────┴────────────────┤
│ Execution Timeline / Streaming Output / Validation Errors   │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 页面区域

#### A. 顶部工作流栏

- 工作流名称和保存状态
- 当前 `GraphState.version`
- 运行全部、停止、撤销/重做（后端支持后启用）
- 工作流整体状态：准备、运行中、等待确认、完成、存在错误
- 连接状态和最近一次 trace ID

#### B. 左侧节点库

- 按材料学任务和节点类型分类
- 搜索节点名称、`tool_id`、数据类型和能力描述
- 显示节点版本、状态和是否可执行
- 拖入画布前展示必要输入、输出和参数摘要
- 不把未审核的 generated/custom 节点伪装成可执行节点

#### C. 中央工作流画布

- 展示节点、端口、连接和分组
- 支持缩放、平移、框选、移动、复制和删除
- 连接时显示源端口/目标端口的数据类型
- 类型不匹配时在连接动作附近给出原因，不静默创建无效边
- 选中节点后显示局部操作工具条
- 运行中突出当前执行路径，但不能只依赖颜色表达状态

#### D. 右侧 Inspector

选中节点后展示：

- 节点标签、`tool_id`、版本和来源
- 输入端口及实际输入摘要
- 参数表单和验证错误
- 输出端口、产物类型和可预览结果
- 当前节点执行状态、耗时和 trace ID
- 运行、停止、重试、跳过、禁用等节点级操作
- 后端返回的路由理由和验证信息

#### E. 底部 Execution Console

- 按时间排列的执行事件
- 节点排队、开始、进度、流式增量、完成和失败事件
- 过滤：全部、当前节点、错误、等待确认、输出
- 显示稳定错误码、用户可读错误信息和重试建议
- 支持展开详细诊断，但不在浏览器展示密钥、授权头或完整敏感输入

## 3. 领域模型与前后端映射

前端计划围绕以下稳定对象组织组件和状态，不直接围绕 Python 内部对象建模：

| 领域对象 | 前端用途 | 后端权威来源 |
| --- | --- | --- |
| `ToolSpec` | 节点库、节点标题、端口、参数和能力说明 | 能力注册表 |
| `NodeInstance` | 画布中的一个节点 | `GraphState.nodes` |
| `Port` | 输入/输出连接与类型提示 | `ToolSpec.input_types/output_types` |
| `Edge` | 节点之间的数据关系 | `GraphState.edges` |
| `GraphPatch` | 新建、移动、连接、删除和参数修改意图 | `POST /api/patch` |
| `RouterDecision` | 候选工具、选中工具、理由和确认要求 | `POST /api/route` |
| `ExecutionResult` | 单节点或任务的最终执行结果 | `POST /api/execute` |
| `ExecutionEvent` | 流式执行期间的增量状态 | 待定的事件接口 |
| `Artifact` | 表格、报告、图片或其他节点产物 | 执行结果/产物接口 |

### 3.1 前端本地状态边界

前端可以本地保存：

- 画布视口、选中节点、展开面板、过滤条件
- 正在编辑但尚未提交的表单草稿
- 事件列表的展示排序和折叠状态

前端不能自行决定：

- 工具是否兼容
- 端口类型是否可以连接
- 节点是否具备执行条件
- 路由选择和科学假设
- 图的最终版本和执行结果

所有图变更都必须携带 `base_version`，由后端确认后刷新服务端状态。

## 4. 流式执行状态设计

### 4.1 节点状态

在现有 `ready/running/completed/waiting/error` 基础上，前端需要区分展示状态：

```text
ready
  → queued
  → running
  → streaming
  → completed

running/streaming → failed
running/streaming → cancelled
任意可恢复状态   → stale（本地视图落后于后端）
```

`queued`、`streaming`、`cancelled`、`stale` 如果尚未纳入后端规范，应先作为 API 契约变更讨论，不能只在前端造出这些状态。

### 4.2 建议的事件契约

此部分为后续后端设计输入，当前不实现：

```json
{
  "event_id": "evt-001",
  "event_type": "node.output.delta",
  "trace_id": "trace-001",
  "task_id": "task-001",
  "execution_id": "exec-001",
  "node_id": "qc-1",
  "graph_version": 12,
  "sequence": 7,
  "at": "2026-09-23T00:00:00Z",
  "payload": {
    "channel": "report",
    "delta": "检查完成 60%"
  }
}
```

建议事件类型：

```text
workflow.started
node.queued
node.started
node.progress
node.output.delta
node.waiting_for_confirmation
node.completed
node.failed
node.cancelled
workflow.completed
workflow.failed
```

前端通过单一事件 reducer 更新执行视图，不能由多个组件分别监听并自行推断状态。事件必须支持 `sequence` 或等价的顺序信息，以便处理重复事件、断线重连和过期事件。

## 5. 节点交互规范

### 5.1 基础操作

- 单击：选中节点并打开 Inspector
- 双击：进入节点参数编辑
- 拖拽端口：创建连接，并实时显示类型兼容性
- 右键：打开节点级上下文菜单
- 复制/粘贴：生成新的节点实例，不复用原节点 ID
- 删除：先形成待提交的 `GraphPatch`，后端确认后更新画布
- 拖动：视口位置可本地响应，但持久化位置需遵循现有图变更策略

### 5.2 执行操作

- 运行节点：只提交明确的节点执行意图
- 运行下游：由后端根据依赖关系决定可执行范围
- 停止：取消对应任务或执行，不直接把节点改成完成
- 重试：携带原始执行上下文和新的执行意图，并生成新的 execution ID
- 跳过/禁用：必须在 GraphState 中有明确语义，不能只改变 CSS
- 人工确认：节点进入 `waiting` 时，界面展示问题、选项和确认记录

### 5.3 错误处理

错误必须同时出现在三个位置：

1. 出错节点的状态和局部提示；
2. Inspector 中的可读错误、错误码、trace ID 和重试建议；
3. Execution Console 中的完整事件上下文。

禁止只显示 “Request failed” 或只把错误写到浏览器控制台。

## 6. 视觉方向

目标是“科研工作台”，而不是“游戏化节点画布”或“纯黑色编辑器”。

- 画布应保持较高信息密度，但节点内部有清晰的标题、状态、端口和结果层级。
- 状态颜色只表达状态，不能同时承担数据类型、选中态和警告态。
- 采用明确的中性背景、少量强调色和统一的状态色；不要让每个节点都拥有强烈独立色彩。
- 当前执行路径可以使用轻量动效，但只用于说明变化，不使用持续闪烁制造噪声。
- 主要操作按钮与其影响范围保持空间邻近。
- 桌面端优先，但至少保证 1280px 宽度下画布、Inspector 和 Console 不互相遮挡。
- 重要信息不能只靠颜色表达；必须同时使用文字、图标、形状或进度。
- 遵循键盘焦点、最小点击区域、WCAG AA 对比度和 `prefers-reduced-motion`。

## 7. 分阶段开发计划

以下阶段只表示顺序，不代表当前已经开始执行。

### Phase 0：前端基线审查

- 盘点现有 `frontend/src/main.jsx` 和 `style.css` 的状态、组件和 API 调用。
- 记录当前 v0.1 画布、对话区、设置抽屉和节点库的实际行为。
- 列出当前 API 与计划目标之间的缺口。
- 产出：前端现状清单、问题截图、API 缺口表。

### Phase 1：确定交互与领域契约

- 固化节点、端口、边、执行、事件和产物的前端 TypeScript/JSON 类型。
- 明确 `GraphState`、`GraphPatch`、`ExecutionResult` 与前端状态的映射。
- 设计流式事件接口、顺序、重连、重复事件和过期事件处理。
- 产出：前端状态模型、事件契约草案、契约测试清单。

### Phase 2：工作台骨架

- 拆分当前单文件界面为工作流栏、节点库、画布、Inspector、Execution Console 等边界清晰的组件。
- 保留后端作为唯一业务规则来源。
- 首先实现 loading、empty、error、version conflict 和 waiting 状态。
- 产出：可导航的工作台骨架，不改变后端执行语义。

### Phase 3：节点与连接操作

- 实现真实的节点库搜索和节点摘要。
- 实现节点选择、Inspector、端口显示、连接预览和兼容性错误展示。
- 所有图变更通过 `GraphPatch` 提交，并在成功后用服务端 GraphState 刷新。
- 产出：可编辑但受后端校验约束的工作流图。

### Phase 4：执行与事件时间线

- 接入节点运行、停止、等待确认、完成、失败和重试。
- 接入事件流或轮询降级方案。
- 建立单一执行状态 reducer，处理顺序、重复、断线和过期事件。
- 产出：用户可以看懂一次执行从排队到结束的全过程。

### Phase 5：科研结果与调试体验

- 将 EIS 导入、列映射、QC 和 Nyquist 输出作为第一条垂直闭环。
- 在节点和 Inspector 中展示输入摘要、QC 报告、图形产物和 trace 信息。
- 增加无效连接、字段缺失、人工确认和执行失败的可恢复路径。
- 产出：可审计的 EIS 工作流 WebUI。

### Phase 6：视觉打磨与可访问性

- 建立颜色、间距、字体、节点状态和结果产物的设计 Token。
- 用桌面和窄屏截图进行视觉复核。
- 检查键盘操作、焦点、对比度、点击区域和减少动效模式。
- 产出：稳定的视觉系统和无障碍验收记录。

## 8. 验收标准

### 交互验收

- [ ] 用户可以从节点库找到节点，并看到版本、输入、输出和可执行状态。
- [ ] 用户可以创建连接，并在类型不匹配时看到明确原因。
- [ ] 用户可以选中节点、编辑参数、提交变更并看到新的 GraphState 版本。
- [ ] 用户可以运行单节点或后端允许的执行范围。
- [ ] 用户可以看到排队、运行、流式输出、等待确认、完成、失败和取消状态。
- [ ] 用户可以从出错节点定位到错误码、trace ID、原因和重试入口。
- [ ] 浏览器刷新或短暂断线后，界面不会把本地旧状态误认为执行成功。

### 契约验收

- [ ] 前端不复制端口兼容、参数校验、路由和科学决策规则。
- [ ] 每次 GraphPatch 都携带 `base_version`。
- [ ] 前端只展示服务端确认后的图状态和执行结果。
- [ ] 事件能够按顺序合并，重复事件不会重复追加输出。
- [ ] 过期 GraphState、过期事件和版本冲突有独立界面状态。
- [ ] 不向浏览器状态、持久化数据或日志写入 API key 和敏感原始输入。

### 第一条垂直闭环

```text
上传 EIS CSV
  → 检查与列映射
  → 创建/展示 typed workflow graph
  → 执行基础 QC
  → 展示结构化 QC 结果
  → 执行或展示 Nyquist 输出
  → 查看完整 trace 与节点事件
```

## 9. 明确暂不执行的事项

- 暂不修改 `frontend/src/main.jsx` 或 `style.css`。
- 暂不新增流式接口或改变后端状态枚举。
- 暂不安装新的前端依赖。
- 暂不进行 ComfyUI 视觉仿制或大规模换肤。
- 暂不启用自动生成工具、未经审核的 custom node 或 Tool Manager 高级能力。
- 暂不把任何前端本地状态提升为后端业务真相。
