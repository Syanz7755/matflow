# 完整阻抗谱提示词：纯后端重跑报告

> 历史快照：本报告记录的是 2026-09-30 当时工作区的行为。随后开发中的后端重新提供了受轮次限制的 `/api/chat`；这里保留原始结果作为回归证据，不代表 2026-10-01 的当前接口状态。当前判断以 `docs/PROJECT_STATUS.md` 和代码测试为准。

## 总结

MatFlow本次没有形成计划、没有生成领域工具，也没有构造工作流。最终图保持Graph v0、0节点、0连边。因此“必须是非单链DAG”的验收条件明确失败；这不是拓扑规划得不好，而是当前后端根本没有执行规划阶段。

当前架构中，MatFlow核心后端是工作区、类型校验、路由、GraphPatch验证和执行权威，不再内置LLM代理。`POST /api/chat`返回“built-in agent is retired”，要求外部AI客户端通过版本化HTTP API或独立MCP bridge工作。本次没有打开遗留开关，因为那只适用于迁移，不能代表当前产品路径。

## 预期的非单链结构

完整任务合理的拓扑应至少包含以下分支、汇合和门控：

```text
                            ┌─ 炉程文档解析 ─┐
上传与检查 ─┬─ 原始扫描解析 ┤                ├─ 时间→温度映射 ─ Cp/G→Z ─ 按温度分组
            └─ 元数据/单位 ─┘                │
                                             ├─ 数据完整性/频率覆盖 ─┐
                                             ├─ KK/Lin-KK物理一致性 ├─ 质量汇总 ─ 质量门控
                                             └─ 多候选电路拟合比较 ─┘              │
                                                                       ┌─ 不通过：问题定位/重测建议
                                                                       └─ 通过 ─┬─ DRT/过程分解
                                                                                ├─ 等效电路贡献比例
                                                                                └─ 图形与报告汇总
```

它至少需要三个分支点、两个汇合/门控点，并且质量不通过时不能调度机理贡献节点。

## 路由对照

| 输入版本 | 候选数 | 选择 | 结果 |
|---|---:|---|---|
| 中文原文 | 0 | 无 | 要求人工确认 |
| 第一次normalize，意外翻译成英文 | 6 | `ebrick_case05_import` | Jev分歧，要求人工确认 |
| 加同语言保护后的中文normalize | 0 | 无 | 要求人工确认 |

英文版本的六个候选全部被词法评分推到100%，并没有获得更准确的阶段规划。Laya选择一个旧的AI修订导入节点，semantic模型选择通用导入节点，最终路由结果又选择EBrick导入别名。这说明提升主要来自当前路由器只识别英文词元，并非结构化normalize让系统理解了复杂任务。

换言之：normalize后的英文文本提高了召回率，但没有提高选择质量，更没有生成多节点DAG。

## 工具构造结果

`prompt-build`对中文原文生成的标签是`1 2 3 4 5 6 NyquistBode`，对中文规范化版本生成`1 ... 2 ... 3 ... 4`；这是因为构建器会删除非ASCII字符。英文漂移版本得到较可读的标签`Context The user provides attachments containing`。

但三个模板的实际契约完全相同：

```json
{
  "category": "Derived",
  "inputs": {"input": "TypedTable"},
  "outputs": {"output": "TypedTable"},
  "params": {"method": "default"}
}
```

它们没有炉程解析、Cp/G到阻抗转换、KK诊断、电路拟合、DRT、质量门控或数值实现，也没有自动注册。因此不能称为“写出了工具”。

## 是否应对每条输入强制normalize

不建议把LLM normalize作为不可绕过的唯一入口。建议采用双轨制：

1. 原始提示词始终作为权威记录，永不覆盖。
2. normalize结果作为派生的规划/检索视图，并和原文一起交给规划器。
3. 对文件名、路径、数字、单位、否定词、条件语句、质量门控和拓扑要求做程序化保真检查。
4. normalize失败、语言漂移或约束减少时自动回退原文。
5. 如果目标只是改善英文词法检索，单独生成`retrieval_query_en`，不要把整条用户请求翻译后替换原文。
6. 记录模型、版本、输入哈希、normalize输出和差异，便于审计。

本次第一次normalize把中文改成英文，已经证明单靠系统提示不能保证语义保真。脚本随后增加了同语言硬校验，并通过五项单元测试。

## 当前最关键的产品缺口

1. 当前产品路径缺少真正的外部AI规划客户端或已连接的MCP代理，因此完整提示词无法进入“读附件→研究方法→生成工具→打GraphPatch→验证→执行”循环。
2. 上传/检查层不能读取Markdown或普通规则文本，炉程数据无法进入规划上下文。
3. 路由器中文召回为零；英文召回又被停用词和大量100%并列污染。
4. 工具管理的search/adapt/build开关均关闭，EIS领域工具配方也不在现有XRD/FTIR声明式配方能力内。
5. 当前类型系统无法表达多个诊断Artifact的汇合、质量门控以及门控后的条件执行。

因此，下一步不是继续调整这一条prompt，而是先补齐外部规划代理、可读文档类型、多语言检索、领域工具生命周期以及DAG门控语义。
